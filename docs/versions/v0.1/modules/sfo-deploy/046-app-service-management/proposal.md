## Background and Goal

当前框架只定义 `check/install/configure/deploy/start/stop/restart` 脚本动作及执行顺序，App
的配置最终 写入、服务启停、配置变化后的 reload/restart、健康判断和失败恢复主要由各 App
脚本自行实现。这保留了 灵活性，但同类 App
容易形成不同语义，框架也无法统一判断幂等、变更、超时和恢复结果。

目标是在不破坏现有脚本型 App 的前提下，为常见 Linux 服务提供内置、声明式管理：首版支持 systemd
服务与配置文件投递，框架统一编排配置、服务动作和部署后的必要 reload/restart；同时优化 App
工件、脚本、
模板等文件向集群节点的传输。配置采用两阶段生成：控制端先生成不含秘密的完整配置骨架并上传，目标节点再由
sfo-deploy 自带的固定变量更新器注入 KEY、密码等声明秘密。固定更新器首版内置 YAML、JSON、TOML、INI
四种结构化格式；无法用内置格式表达的配置可显式选择受限的配置更新脚本。其他内置能力无法覆盖的 App
继续 使用受现有运行时权限约束的自定义生命周期脚本。

## Scope

### In scope

- 为 App 配置增加可选、版本化的内置管理声明，首个内置服务管理器为 systemd。
- systemd 模式声明受校验的 unit 名称、启用策略、部署后动作及相关超时；框架使用固定 argv 和现有
  root/`sudo -n` 预检执行服务查询、启动、停止、重启、reload 和 daemon-reload 中实际需要的子集。
- 为 App 增加声明式配置文件投递：明确模板来源、绝对目标路径、权限、普通变量、秘密变量以及可选的配置
  校验命令；配置内容未变化时报告 unchanged。
- 配置采用两阶段生成。控制端负责校验模板语法、变量声明和目标路径，解析全部非秘密参数并生成确定性的
  配置骨架；骨架只保留与声明绑定、不可歧义的秘密占位符，不读取目标节点秘密，也不包含秘密值。
- 控制端生成的配置骨架与普通 App 文件一起进入不可变传输清单并上传。目标节点运行 sfo-deploy 自带、
  与框架版本绑定的变量更新器：首版内置 YAML、JSON、TOML、INI 四种结构化编辑器，分别通过受校验的
  字段路径或 INI section/key 定位完整值；更新器从逐步骤秘密副本读取 KEY、密码和文件秘密，按声明类型
  写入候选配置，不用 shell、`sed`、正则或模糊文本替换秘密。标准内置模式不执行 App 自定义 `configure`
  脚本。
- 对 YAML、JSON、TOML、INI 之外的格式，或结构化编辑器无法保留的 App 特有语义，允许 App 显式声明
  `script` 配置更新器。脚本必须来自本次不可变传输清单并绑定摘要，使用固定 argv 接收输入骨架、独立
  输出候选文件、只读绑定清单和秘密目录路径；秘密值不得通过 argv 或普通环境变量传递。脚本在非特权 App
  身份下运行，受超时、取消、输出大小和路径边界限制，退出成功后仍须通过框架的完整性、权限、残留占位符
  及可选配置校验，再由框架原子发布；脚本不得直接覆盖最终目标或控制 systemd。
- 远端变量更新器和脚本适配器必须拒绝缺失秘密、未知或残留占位符、重复目标、无效字段路径、类型不匹配、
  无效编码及越界输出；候选配置通过格式复解析和可选的固定 argv 校验命令后才原子替换持久目标。失败时
  保持旧配置不变并清理骨架、候选文件和秘密副本。
- 秘密不得进入 CLI 参数、普通环境变量、传输清单、控制端生成物、发布快照、日志或错误文本；最终含秘密
  配置不得从目标节点回传。发布历史只保存不含秘密的骨架摘要、声明和执行结果。
- 优化 App 文件投递：框架为每个 App/目标节点建立不可变传输清单，记录相对名称、用途、长度和强摘要；
  控制端在下载并校验原始 App `tar.gz` 后，将该原始包、App 目录中声明的脚本、无秘密配置骨架和步骤所需
  普通文件连同清单封装为单个外层 `tar.gz` 部署包，减少逐文件 SCP 与 chmod 往返。原始下载包作为部署包
  内的独立成员保留，不在控制端重新生成其内容；目标节点只有在安全解开外层包并逐项校验清单后，才允许
  安装、配置或部署步骤消费其中内容。
- 外层部署包采用固定布局，至少区分 manifest、原始 package、scripts、config skeletons 和普通 files；
  成员路径、用途、长度、强摘要及期望模式来自控制端清单，脚本的可执行属性由声明恢复而不是信任归档元数据。
  目标节点先把单一部署包写入 release attempt
  专属暂存路径并验证外层摘要，再安全解包、校验全部成员与原始 package
  摘要，随后从暂存根目录执行安装；任一步骤失败都不得消费部分解包内容。
- 同一目标节点、同一 release attempt 内按内容摘要复用已经校验的普通文件，避免相同 App 包或共享输入被
  重复封装或上传；复用单位优先为完整部署包，不能证明整个部署包一致时才退回成员级构建复用。秘密副本仍
  保持逐步骤最小暴露、独立投递和及时清理，不进入外层部署包，也不参与普通文件复用。
- 批量包或清单的创建、解包必须拒绝绝对路径、`..`、链接、设备文件、重复项和越界大小；失败、取消或校验
  不一致时清理暂存区，不发布半成品。首版基于现有 OpenSSH 传输，不要求目标机安装 Agent 或 rsync。
- 文件投递优化包含修正当前 `packageCache` 在执行器中的传递偏差，确保 deploy 使用已预检并固定的同一
  本地工件，而不是在执行准备阶段再次调用 package provider。
- 把配置变更通知与服务动作关联；一次 App 操作中的多个变更合并为至多一次 reload/restart，并明确
  `deploy`、内置两阶段 `configure` 以及独立 `start/stop/restart` 命令的顺序和失败语义。
- 保留当前脚本机制作为自定义扩展路径。未声明内置管理的 App 完全沿用现有行为；内置动作与同名自定义
  动作不得形成不明确的双重所有权，配置装载阶段必须拒绝冲突声明。
- App 特有的安装、迁移、流量处理、第三方服务操作或内置配置契约无法表达的生成逻辑，仍可通过受权限声明
  约束的自定义脚本完成；设计阶段明确内置阶段前后的有限 hook，而不加载任意本地插件模块。
- 保持秘密按步骤最小暴露；配置生成只获得声明的秘密，日志、计划、结果和错误不得泄漏秘密值。
- 更新公共 API 类型、CLI/JSON 结果中必要的兼容字段、文件投递/配置生成结果、示例集群和中文配置指南。
- 增加单元、DV、集成和契约验证，覆盖幂等、动作顺序、提权、超时、部分失败、清理、兼容和秘密脱敏。

### Out of scope

- 首版不内置 Windows Service、OpenRC、SysV、容器编排器或进程守护器；它们继续使用自定义脚本。
- 不引入目标机常驻 Agent、第三方插件发现机制或在部署机动态加载不受信任代码。
- 不新增 rsync、对象存储客户端或专用传输服务依赖，不把“优化”定义为绕过摘要校验或安全清理的最快上传。
- 不把控制端外层封装视为重新构建、修改或提前安装原始 App
  `tar.gz`；原始包保持字节级内容和摘要，目标端 安装过程按 App 声明消费它。
- 不把秘密打入 App 安装包、普通批量传输包或 release snapshot，也不把目标机秘密反向下载到部署机渲染。
- 不允许控制端读取目标节点秘密，也不允许标准 YAML、JSON、TOML、INI 模式通过远端 App 自定义脚本
  生成配置；脚本只能由配置文件显式选择为独立的 `script` 更新模式，不能与同一文件的内置结构化更新器
  混用，也不能隐式退回脚本。
- 不在首版实现多机滚动发布、服务发现摘流量、蓝绿/金丝雀策略或跨机器事务。
- 不自动迁移已有 App YAML 和脚本，也不改变未选择内置管理模式的既有部署结果。
- 不把数据库 migration 或外部系统写入纳入通用自动回滚承诺。

### Boundary with neighboring modules

- `config/types` 拥有声明和严格校验；`planning` 拥有稳定步骤及依赖顺序；控制端配置组件拥有模板契约、
  非秘密变量解析与骨架生成；文件投递组件拥有内容清单、本地固定和目标端校验；框架远端变量更新器只拥有
  秘密占位符替换；`execution/transport` 拥有受限远端原语、资源清理和结果；App 脚本只拥有明确交给
  自定义扩展的行为。
- systemd 是目标机已存在的外部依赖。框架负责探测和调用，不负责安装 systemd 或创建操作系统。
- 发布历史继续记录实际执行计划和结果；通用回退只恢复框架可证明拥有的版本/配置状态，不承诺撤销 App
  自定义脚本产生的外部副作用。

## Requirement Review

该方向合理：控制端更适合处理非秘密模板与普通参数，可在连接目标前发现大多数配置错误；目标端只处理无法
离开节点安全边界的秘密替换。把两者通过显式占位符契约连接，比让每个 App 在远端重复实现模板解析更容易
统一幂等、权限、完整性、错误和可观察性，同时仍保留脚本逃生口覆盖特殊 App。

首版选择“显式 opt-in 的内置管理 + 现有脚本兼容模式”，而不是让框架猜测 App 是否由 systemd 管理。
这会增加 schema 和执行状态机复杂度，但能避免隐式接管线上服务。自定义扩展首版复用现有独立脚本协议并
增加有限 hook；暂不设计动态插件 ABI，以免扩大供应链和部署机代码执行边界。标准内置配置不执行 App
`configure` 脚本，只执行框架固定变量更新器及可选验证 argv。首版直接支持 YAML、JSON、TOML、INI，
这些格式使用结构化字段定位而不是通用字符串插值；App 专用格式必须显式选择受限 `script` 更新器，脚本只
生成候选文件，校验、权限和原子发布仍由框架拥有。文件投递采用“部署机固定并校验一次、目标机按摘要验证并
复用”的控制端推送模型：把保持原始字节的下载包与 App 脚本、无秘密配置骨架和清单组合成一个外层
`tar.gz`，每个目标通常只上传和解开一次，不在执行中再次从 package provider 获取另一份内容。

## Success Criteria

- Concrete user-visible or system-visible result: 用户可在 `app.yaml` 显式选择 systemd
  内置管理；框架在 控制端生成无秘密配置骨架，并将它与 App 目录声明脚本、普通文件及保持原始字节的下载
  `tar.gz` 封装为 单个外层部署包上传；目标节点安全解包和校验后再安装，可用框架内置
  YAML、JSON、TOML、INI 结构化 更新器注入 KEY/密码，特殊格式可显式使用受限 script
  更新器生成候选文件，再由框架统一校验、原子发布 并完成服务生命周期；其他不受支持的 App
  行为可继续用自定义生命周期脚本；现有 App 默认行为不变。
- Required evidence: schema/契约测试、逐分支单元测试、包含传输复用/篡改、秘密渲染、成功与失败恢复的
  DV、
  真实命令边界集成测试、示例计划验证和中文文档全部通过任务级统一入口；独立验收审查权限、完整性、幂等、
  顺序和回退缺口。
- Explicit non-goals: 不承诺跨机器原子发布，不内置 systemd 之外的服务管理器，不自动回滚自定义脚本
  的外部副作用，不引入常驻 Agent 或动态插件加载。

## Risks

- systemd 操作通常需要提权；unit 名称、目标路径、owner/mode 和验证命令若校验不足，会形成命令注入、
  路径逃逸或权限提升风险。
- 配置已经替换但服务动作失败时可能出现“磁盘新配置、进程旧配置”的部分完成状态，设计必须明确恢复或
  可操作的失败结果，不能仅返回脚本退出码。
- deploy、configure 和显式 restart
  并发可能互相覆盖；必须复用或扩展现有集群操作锁，并明确跨进程边界。
- 配置内容可能包含秘密；暂存、哈希、日志、错误、发布快照和清理路径都必须维持最小暴露和脱敏。
- 批量传输和目标端复用若把“路径相同”误当成“内容相同”，可能执行陈旧或被替换的文件；复用键必须绑定
  强摘要和用途，并在消费前验证。
- 批量归档扩大了解包攻击面；清单、成员类型、路径、数量和总大小必须在本地与目标端双重限制。
- 外层部署包包含内层 App
  `tar.gz`，实现若递归信任内层路径或在校验前展开安装内容，会形成归档炸弹、路径
  穿越或符号链接逃逸；外层与内层必须分别受摘要、成员数量、展开大小和安全路径限制，安装只能消费完成校验
  并原子标记就绪的暂存目录。
- 远端变量更新器会接触秘密；它必须是框架固定组件，只接受控制端已验证的骨架和绑定声明，输出使用最小
  权限，异常信息不得包含输入值，失败后必须清理秘密副本和候选配置。
- 不同配置格式对引号、换行和二进制值的转义要求不同；秘密占位符必须显式声明编码方式，不能猜测 YAML、
  JSON、shell 或 properties 语义，否则可能生成可解析但含义错误的配置。
- YAML、JSON、TOML、INI 的数据模型并不完全相同，尤其是 YAML 标量类型、TOML 类型以及 INI 的重复键、
  注释和大小写规则；设计必须定义支持的字段路径、类型保持和序列化规范，并对无法无歧义处理的输入失败关闭。
- 配置更新脚本可读取秘密并生成任意内容，是比内置结构化更新器更大的信任边界；必须显式
  opt-in、摘要绑定、 非特权执行且不能访问最终发布路径或 systemd
  控制面，并通过框架后置校验，文档中需明确其安全责任归 App。
- 内置与自定义扩展若同时拥有同一动作会导致重复启停；必须在配置期拒绝歧义，而不是依赖执行顺序碰巧正确。
- 旧 App 的兼容性优先；任何默认接管或隐式 restart 都可能造成生产中断，因此新行为必须显式 opt-in。
