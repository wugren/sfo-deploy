## Background and Goal

现状：秘密值由项目绑定（`ProjectBindings`）在 CLI 侧提供；`config_secrets` 在每次
`configure`/部署时写入临时 JSON context （`DEPLOYMENT_CONTEXT_PATH`）注入脚本，`file_secrets` 在
`configure` 时临时投递到目标路径。不存在独立的、可重复执行的
“把密钥部署到集群设备”这一步骤，脚本也只能从上下文 JSON
读取，不能以其运行环境中的环境变量方式消费秘密。

目标（用户已明确方向）：采用“编排端解密、渲染并常驻节点文件”的模式（对应 Puppet Hiera eyaml / Chef
encrypted data bags / SaltStack Pillar
的思路）——新增一条独立命令，把项目绑定的密钥部署到目标集群设备的某一安全目录（固定路径、受限权限、
原子写入、幂等、可审计）；之后**只有在执行 app 或 environment
脚本时**才读取该安全目录，把声明给该脚本的密钥装载给脚本进程，
让脚本能够获取密钥。密钥包含两类形态：**值密钥**（密码、token
等，装载为字符串）与**文件密钥**（证书、私钥等，装载为
受限路径，脚本打开读取），两类都通过同一个受限读取 API
获得。密钥到节点的放置必须在集群声明中**显式指定** （具体机器列表，或通配符 `*`
部署到集群全部节点），**默认不部署**——未声明的密钥不会出现在任何节点上。
集群侧持久存在的是“安全目录中的密钥文件”，而不是长期运行进程的环境变量；加载动作只发生在部署脚本执行期间。
同步更新示例、文档与测试。

## Scope

### In scope

- 新增独立 CLI 动作（暂名
  `secrets-deploy`），把绑定密钥部署到集群全部或所选机器的安全目录；支持按环境/App
  分组、幂等更新与审计。
- 集群/环境/App YAML
  的密钥声明扩展：声明所需的值密钥与文件密钥名称、目标目录，以及哪些脚本在哪些动作中应获得密钥。
- 密钥放置声明：每个密钥显式指定目标机器（`machines: [名称, ...]`）或使用通配符 `*`
  部署到集群全部节点；未声明的密钥默认 不部署到任何节点；`secrets-deploy` 的目标与 `--machine`
  筛选相交，未知机器名、名称重复或冲突声明校验失败。
- 远端安全目录的创建、模式/属主约束、原子写入与覆盖/删除语义；未绑定或未部署密钥时的失败关闭行为。
- 部署脚本执行时的密钥装载：执行 app/environment 脚本的短暂进程经受限读取 API
  获得声明的密钥（密钥值不经环境变量、 不进入长期运行进程、不写入常规结果输出）。
- 移除旧机制：删除 `config_secrets`/`file_secrets`/context JSON
  相关路径与语义，示例、测试、文档全部迁移到新机制， 不再保留兼容路径。
- README、配置指南、CLI 帮助与 Multipass 示例迁移到新模式；相关测试补齐。

### Out of scope

- 不实现密钥生成、轮换、加密存储或 vault
  集成；密钥值仍由项目绑定按现有安全边界提供（除非用户在未决问题中另有选择）。
- 不改变通用 `sfo-deploy` CLI“无项目秘密绑定即失败关闭”的原则。
- 不修改发布历史、下载缓存、回滚等无关生命周期。
- 不引入新的机器可读日志/事件流格式。

### Boundary with neighboring modules

- secrets 模块：扩展 `ProjectBindings`/部署目标描述与脱敏，保持“值不落 YAML、不进结果
  JSON”的既有边界。
- execution/transport：新增秘密部署步骤与脚本启动时的环境装载，不改变现有步骤顺序语义（check→install→configure→start/restart）。
- planning/config：新增声明字段的校验与放置映射；`validate` 输出仍不含秘密。

## Requirement Review

需求方向合理：把“秘密随执行临时注入”改为“先独立部署到集群侧安全目录、执行时再加载”，职责更清晰，密钥状态可独立查看、复核与
审计，也便于脚本与服务进程稳定消费同一份秘密。

主要风险与取舍：

1. 环境变量可见性：注入远程进程环境后可在宿主侧 `/proc/<pid>/environ`
   或命令回显中观察，暴露面与现有临时 JSON context 不同； 设计阶段需要确定注入载体（直接 set env vs.
   脚本以受限 API 从安全目录读取后自行导出）并对日志/输出继续脱敏。
2. Deno/Python
   权限模型：当前远端脚本启动命令没有为任意环境变量授予读取权限，需要按需收窄允许名单或在框架提供读取
   API。
3. 迁移成本：用户已决定移除旧机制（`config_secrets`/`file_secrets`/context
   JSON），示例、测试、文档与既有消费方需一次性 迁移，属于破坏性公开契约变更。
4. 安全目录读取权限：脚本以 SSH 用户运行，若目录 root `0700`
   则脚本需要提权；目录默认位置、归属与模式需要固化。

选择方向：以“独立部署命令 + 集群侧持久安全目录 +
部署脚本执行时装载”作为本次主路径；旧机制（`config_secrets`/ `file_secrets`/context
JSON）按用户决定（Q2=B）移除，不保留兼容路径。
关于装载载体，发现一个实现层面的重要事实：当前远端命令通过 `env NAME=value <command>`
字符串拼装环境变量 （`src/transport.ts` `OpenSshRemoteSession.run`），若直接把密钥值放进
env，值会短暂出现在本机 `ssh` argv 与目标机 `/proc/<pid>/cmdline`（`ps`
可见），并被脚本子进程继承。因此默认建议沿用“路径/上下文”方式（脚本经受限读取 API 或
`DEPLOYMENT_CONTEXT_PATH` 指向的安全目录文件读取），把密钥值放进 env
仅作为显式声明的可选载体（Q1）。 读取 API
必须同时覆盖两类密钥：值密钥返回字符串（空值/缺失失败关闭），文件密钥返回安全目录内的绝对路径（脚本自行打开读取，
避免把证书等大内容整块载入内存或写进日志）。
放置语义：密钥按“节点”维度管理，放置声明写在集群级配置（见
PI-3/PI-6）；运行期脚本无法枚举安全目录，只能按声明名称读取，
密钥未放置到该节点时以明确的“未部署到此机器”错误失败关闭。

## 读取 API 草案（B 方案，待用户确认后固化）

框架在脚本步骤开始时注入**仅含路径**的环境变量 `DEPLOYMENT_SECRETS_DIR`；Deno
白名单增加该变量并把安全目录加入 `--allow-read`。随步骤上传受限 loader 模块，脚本以相对导入使用：

```ts
// sfo-secret-loader.ts（框架提供，随脚本步骤上传到同一 workspace）
const secrets = await loadSecrets({
  dir: Deno.env.get("DEPLOYMENT_SECRETS_DIR")!,
  values: ["ELEPH_DB_PASSWORD"], // 值密钥：返回非空字符串
  files: ["TLS_SERVER_KEY", "TLS_SERVER_CERT"], // 文件密钥：返回受限绝对路径
});
secrets.values.ELEPH_DB_PASSWORD; // string
secrets.files.TLS_SERVER_KEY; // 绝对路径，脚本以只读方式打开
```

```python
from sfo_secret_loader import load_secrets

secrets = load_secrets(
    dir=os.environ["DEPLOYMENT_SECRETS_DIR"],
    values=["ELEPH_DB_PASSWORD"],
    files=["TLS_SERVER_KEY"],
)
```

安全目录布局（默认
`~/.sfo-deploy/secrets/`，按节点独立，可按机器配置路径）：只有被放置到该节点的密钥才会出现；
每个密钥一个文件，文件名即密钥名（`^[A-Z][A-Z0-9_]*$`），目录 0700、文件
0600；值密钥文件内容为原始值（无尾随换行），文件密钥为原始字节 （loader
只校验文件存在且为普通文件）。缺失、空值、非法名称、重复声明均立即报中文错误并终止步骤，错误只含密钥名。
loader 自身不打印、不写日志、不把内容放入子进程
env，返回内容只在脚本内存中存在（文件密钥由脚本按路径自行读取）。

## Risks

- 安全边界：密钥以明文文件持久存在集群设备上，保护依赖目录/文件权限与平台访问控制；若采用 env
  注入，值还会出现在本机与目标机 进程 argv/cmdline（`ps` 可见）并被子进程继承，而
  `/proc/<pid>/environ` 同权限可读；设计阶段必须固化目录归属、模式、
  覆盖/删除、装载载体与失败关闭语义。
- 公开 CLI 契约：新增动作与注入语义属于公开接口变更，帮助、文档与示例必须同步。
- 兼容/迁移：移除旧机制是破坏性公开契约变更，既有集群、示例与测试必须一次性迁移；设计阶段固化删除清单（YAML
  字段、读取 API、 上下文文件、文档与符号引用），验收做旧符号无引用扫描。
- 脚本权限模型：Deno `--allow-env`/Python 环境访问需要评审，避免为读取密钥放开过宽权限。
- 远端生命周期：安全目录的并发写入、部分失败清理、旧密钥清理与目标冲突需要在设计中覆盖。

### 安全评审发现（2026-09-03，用户要求检查本方案；严重度已在讨论后按受信服务器模型降权）

- 中：同 uid 脚本可直接读全部安全目录（受信服务器模型下与 app
  明文消费属同一信任域，价值有限）。安全目录归属 SSH 用户 （默认 `~/.sfo-deploy/secrets/`），同 uid
  脚本即可直接读全部文件；但这也与 app 最终以明文
  读取渲染配置属同一信任域，并不构成更高威胁。低成本改进：执行期只把**该步骤显式声明的**密钥文件复制进
  0700 workspace 供脚本读取，安全目录本身不进入
  `--allow-read`，避免误读/误泄露，不作为对抗完整攻破的承诺。
- 中：明文持久落盘与快照/备份残留面。Multipass
  快照或磁盘备份会把明文秘密带走，且旧密钥在轮换后仍长期残留； 提供显式移除（如
  `secrets-deploy --remove`）、`--check` 漂移校验，并在文档明示快照/备份会包含明文秘密。
- 中：执行阶段值脱敏失效（设计已接受）。脚本输出无法按值打码；缓解为控制器绑定值在场时仍尽力脱敏、loader
  不打印且错误只含 名称、文档约定脚本禁止输出秘密。
- 中：投递窗口与临时文件。scp 后 chmod 之间存在瞬态权限窗口；临时文件残留会扩大泄露面。设计复用现有
  file_secret 模式： 上传到 0700 workspace → `install -m 0600` → 原子 `mv -T` 落位 →
  结束清理；创建目录用 `mkdir -m 0700` 并拒绝权限过宽。
- 中：放置与漂移。`*` 在每次显式执行 `secrets-deploy` 时按当前 `machines.yaml`
  解析，新节点不会自动获批；需要维护每机 校验清单（仅存哈希，模式 0600）供 `--check`
  核对，防止“节点上密钥过期或被人改动”无感知。
- 低：Python 运行时无沙箱，且部分脚本带 `--allow-net`，理论上可外发秘密；部署脚本是受信代码，loader
  为约定边界，文档明示。
- 低：读取无审计。可审计的只有放置状态与命令历史；如需读取审计需依赖 OS audit，不纳入本次。

### 威胁模型与职责分层（2026-09-03 讨论结论）

目标形态是受信的单信任域节点：app
最终必定以明文消费密钥（部署脚本渲染出配置文件、数据库认证等），任何装载/存储方式都
无法改变这一点；节点被完整攻破（root 或同 uid）时，用户态秘密管理机制都可被绕过。因此：

- 第一类控制（部署方责任，写进运行环境安全前提）：主动保证服务器安全——及时补丁、最小化网络暴露、SSH
  加固、最小权限 用户与 sudo 收口、进程与文件系统监控、备份/快照保护。框架不替代也不承诺实现这些。
- 第二类控制（框架职责）：秘密生命周期卫生，避免在 app
  所需明文之外再制造长期残留的额外明文副本——最小化按节点放置、
  按需暴露、显式撤销与漂移校验、失败关闭、原子落盘、控制端脱敏。
- 第三类控制（文档/约定）：Python
  无沙箱、细粒度读取审计、脚本禁止输出秘密等，作为受信脚本模型的说明，不新增防御承诺。

### 安全评审应对措施（拟进入设计）

1. 暴露边界：准备阶段按每个步骤解析声明的密钥白名单；执行前在远端本步骤 0700 workspace 内建立
   `secrets/` 子目录， 逐文件（文件名一律经 `^[A-Z][A-Z0-9_]*$`
   校验）把安全目录中的对应密钥复制进副本，缺失立即失败关闭；loader 只读该副本， 安全目录整体不加入
   `--allow-read`。对同 uid 脚本，“只可见声明子集”成为强制边界；对“脚本本身受信”的模型，剩余风险
   （sudo、进程环境、受信代码主动外发）写入文档。
2. 生命周期与撤销：`secrets-deploy --remove` 显式移除密钥；`--check`
   只读模式按节点校验清单核对状态；每节点维护 0600
   校验清单（`名称/kind/sha256/时间`）；声明删除但节点仍有残留时 `--check` 报 `extra`。文档明示 VM
   快照与备份包含 明文秘密、建议排除或单独保护；盘上加密明确不在本次范围。
3. 脱敏：`secrets-deploy` 命令自身输出/错误按绑定值脱敏；执行期 loader
   不打印、错误只含密钥名；脚本禁止输出秘密作为 受信脚本模型的文档约定。
4. 投递：完全复用现有 file_secret 原子投递原语（0700 workspace → `install -m 0600` → 原子 `mv -T` →
   结束清理）； 安全目录用 `mkdir -m 0700` 创建，发现已有目录权限过宽时失败关闭。
5. 放置与漂移：`validate` 静态校验机器名、重名与 kind 冲突；`*` 在每次显式执行 `secrets-deploy`
   时按当前 `machines.yaml` 解析，不自动跟随未来新节点；`--check` 对照哈希清单发现缺失/过期/被改。
6. 脚本能力：脚本网络权限继续按现有声明白名单；loader
   不参与任何网络能力授予；受信脚本边界、最小网络白名单写入配置指南。
7. 审计：以放置声明、命令输出与校验清单为审计点；细粒度读取审计依赖 OS
   auditd/AppArmor，明确不纳入本次范围并在文档说明。
